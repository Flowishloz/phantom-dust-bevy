# Skill effects (`Data/Effect/`)

Code: `crates/pd_formats/src/effect.rs` (the `.eft`/ALR layout) + `crates/pd_formats/src/effect_archive.rs` (the packed archive), `pd_convert effects`, playback `crates/pd_game/src/effects.rs` (game `fx.rs`, viewer `crates/pd_viewer/src/fx.rs`). Established 2026-09-26; shaders, slot 2, frame rate 2026-09-27; packed archive as the primary source, ground/air effect from the action table 2026-09-27 (packed-effects lane). Arena-object effects (stage `EF00` records) are in FORMATS-STAGES.md "Object effects".

Legend: ✅ confirmed · ⚠️ assumed / partly verified · ❓ unknown.

## Files

| File | What it is |
|---|---|
| `eftNNNN.alr` (477 loose) | Effect geometry + textures + per-piece timing. Normal ALR container (FORMATS-ALR.md). No animation (0x5) chunks. |
| `eftNNNN.eft` (476 loose, 412 bytes) | Which effect models play at which event slot. |
| `name.lst` | Shift-JIS list "NNNN name" — the developers' effect names. |
| `e.i` + `a0.e`..`a7.e` | **The packed archive the game actually loads every effect from** (PROGRAM-RE.md "Packed effects", `pd_formats::effect_archive`): `e.i` = u16 archive count, u16 entry count (496), then 496 × `(u16 effect number, u16 archive index, u32 byte offset, u32 byte size)`, sorted by number; an entry's bytes are the effect's ALR (padded to 0x800) followed by one 0x800 block whose first 412 bytes are its `.eft` (103 of the 433 numbers that are also loose differ in a few fields from the loose `.eft` — the packed one is what plays). 63 packed numbers have no loose file at all (302–321, some 3xxx/4xxx); conversely 43 loose numbers (the 500s/other shared effects, `pd_convert` reports them as "loose-only") aren't in `e.i` — the game must reach those some other way ❓. `pd_convert effects` reads the archive first and falls back to a loose file only when a number isn't in it. |
| `ecopy.pl`, `x.bat` | Dev scripts that copied eft0517 into 520–550 (placeholders). |

## Skill → effect ✅

**Effect number = the skill's action-table row's effect column (w2)** — `action.ground.effect` / `action.air.effect` in `cache/skills.json` (ground cast / mid-air cast; PROGRAM-RE.md "Packed effects") — **not the skill's text id.** Most skills' ground effect equals their text id (gsdata s2/s5/s12), which is why the two were conflated before this was checked against the program; 82 of 399 skills' ground effect differs from their text id, not only the re-release skills 301–340 (e.g. skill 104 and 283 among the originals too).
Evidence: `name.lst` names match the skills via their action-table effect: 1 サイコウェーブ (Psycho Wave), 8 雷破斬 (Lightning Sword), 9 氷封斬 (Ice Sword), 10 火炎剣 (Flame Sword), 12 虚空斬 (Vacuum Slash), 42 レーザー (Laser), 43 スライドレーザー (Slide Laser), 115 石壁 (Crystal Wall), 123 氷の壁 (ice wall), 125 炎の壁 (fire wall).

Other ranges (from name.lst): 500–517 shared (500 environment debug, 501/502 environment crystal appear/break, **503 generic hit, 504 generic explosion hit exist nowhere** — neither packed nor loose ✅, checked directly against `e.i` and the loose file listing —, 505 life cost, 506 level cost, 507 auto-capture, 508–517 ability restore/erase/seal/status up/down…), 600–609 aura, 700–709 battle start, 1000–9049 bosses.

## `.eft` layout ✅ (all 476 files)

| Off | Size | Meaning |
|---|---|---|
| 0 | 12 × 20 | One entry per effect model; word at +4 is 0x1D or 0x1B ❓ (not blend mode: Crystal Wall shards are 0x1D). Non-zero entry count = model count in the .alr (checked on all files). |
| 240 | u32 | always 0 |
| 244 | 6 × 28 | **Event slots.** i16 flag (1, rarely 5), i16 0, then up to 12 i16 model indices, −1 padded. Every model is referenced exactly once across the slots (all files). |

Slot usage by capsule type (from skills.json): attack 0-1-2-3 (56), 0-3 (21, short-range), 0-1-3 (20), 0-2-3 (14, swords/punches), 0-1-2 (5), Bomb Shot 0-2; defence 0-4-5 (37); environment 0 only.
⚠️ Meaning from renders: **0 = cast (at the caster)**, **1 = projectile body** (Laser: the beam quad), **2 = ground impact** (2026-09-27, was "launch": every slot 2 looked at is a short burst lying at y ≈ 0 — Laser a blue ring, Blaster an orange ring, Bomb a flame on the ground, Bomb Shot an expanding dust ring with lightning, Excalibur red rays; Bomb Shot has no projectile body, only 0 and 2; played at the caster these read as fire at your own feet), **3 = hit on target** (Psycho Wave: shockwave dome; for Laser / Blaster / Bomb slot 3 holds only `90e7fd3e` emitters, so their hit look probably comes from a spawned shared effect — though 503 "generic hit" / 504 "generic explosion hit" exist nowhere at all (neither packed nor loose ✅), so it isn't one of those two numbers ❓), **4 / 5 = barrier block / barrier break** (Crystal Wall: shards). Slot 0 on Crystal Wall is the wall itself.

**Where slots attach**: slots 0 / 3 / 4 / 5 are played on the caster / victim, slot 1 on the projectile facing its travel, slot 2 where the shot ended (facing its travel; blasts unrotated). ~~No joint (hand) attachment is needed for anything looked at.~~ Refuted 2026-09-27 (knifefx lane), below.

**Where pieces attach: on the character bone their joint names** ✅ (2026-09-27, knifefx lane). Effect joints carry packed names (base 40, `alr::joint_name`) and they are the **character skeleton's bone names**: Psycho Knife's `eft0003` model 0 = joints `RHAND` ×4 and `RSWORD` ×2 (the blade piece `m0_d0` on RSWORD, the flash `m0_d1` on RHAND), model 2 (its hit, slot 3) = `BODY2` (the victim's chest). Across all 477 loose effects: `RHAND` 1,169 joints in 174 files, `BODY1` 985 / 149, `RADDHA` 645 / 69, `BODY2` 352 / 123, `RNINOU`, `RTEKUB`, `RFOOT`, `NECK`, `RKATA`, `LNINOU`, `RSWORD` (146 / 21 — the sword skills), `LHAND`, `HEAD`, … ; unnamed (0xFFFFFFFF) 11,214. Every name also exists on the player skeletons (`pc01a`: RHAND 83, RSWORD 91, BODY2 55 — the index differs per character). **The program's rule** (`FUN_140189420`, run per effect model each frame): for each effect joint, build its own TRS; if it is named, look the name up in the playing character's bone table (`FUN_14018a7d0` builds a per-player table of the skeleton's joint names → world matrices, sorted; `FUN_14018aa50` binary-searches it) and place the joint at *bone world × joint local*; an unnamed joint sits on the effect's own matrix (the character root for slots 0/3/4/5). No parent chain: effect joints are all roots (every file). `FUN_14018aaf0` adds 14 two-bone names (`LHRH` = LHAND + RHAND, `LFRF`, `RKRH`, `LKLH`, `B1RH`, `B1LH`, `B1RF`, `B1LF`, `LARA`, `RKRA`, `B1RA`, `B1LA`, `NERA`, `NELA`; strings at `0x1402f31bc…`) whose emitters get both bones' matrices — ours follows the first (`effects::bone_for`) ⚠️. The 0x14 emitter chunks carry their joint too (u16 at payload +0x12, after the material). **This was the cause of Psycho Knife's "small pink smudge near the shins"**: we played every piece at the character root, so the blade (authored in the RSWORD bone's frame, 12 u along +Z) lay at the feet and never moved with the arm. Playback now (`effects::bind_bones`): a piece whose joint names a bone of the host character is re-parented onto that bone node (`p0j<index>` in the character glb; `cache/fx/bones.json`, written by `pd_convert effects` from the same source file and body model `pd_convert character` uses, maps each character's bone names to that index); emitters, blades and flares read the bone's world matrix when they emit. Unknown names (e.g. `SHOT01`, boss names) stay on the root; the program would leave those at the bare joint matrix. Proof: `shots/kfx_pk_before_after_footage.png` (tick-exact, next to Laurence's footage), `kfx_swords_before_after.png` (Mist Blade, Psycho Blade), `kfx_regression.png` (Laser, Psycho Wave, Blaster, Tiger Kick unchanged or following the hand).

**The re-release's extra skills (301–340)** ✅ (2026-09-27, packed-effects lane): their text ids (304–353) mostly have no effect file at all, which is why they used to look like they had none — but they aren't picked by text id. **Beams** ✅: lasers are not stretched to the target. They are ordinary moving projectiles (slot 1: a head quad + a `b8de89ea` trail emitter, grow (1, 1, 20)) that leave a long trail behind them; the length is the emitter's, not the distance.

**Cast effects set shot count and spawn points** ✅ (PROGRAM-RE.md "Multi-shot and spawn points come from the cast effect", 2026-09-27, `FUN_14018a310`): at the fire tick the program scans the caster's slot-0 cast effect (`eftNNNN`) for pieces/joints named **`SHOT01`, `SHOT02`, …** (packed names, base 40, `(name & 0xFFFFFF00) == 0xB3D8C500`) and creates one attack object per marker found, spawned at that marker's position and orientation. So how many shots a skill fires and where from is **authored in the effect file, not the skill table** — the skill table's motion parameters (e.g. Arc's s69, Ricochet's s70) only pick which per-shot angle step each marker's shot gets, not how many shots there are. Motion-13 melee also reads a hit point this way: the `SHOT01` marker of the caster's *currently playing* cast effect, or a caster matrix if there isn't one.

**Shot markers: where they are, what they hold, what the program does with them** ✅ (2026-10-01, lane shotpoints; `FUN_14018a310`, `FUN_1402626d0`, `FUN_14026c340` / `FUN_14026c730`; `pd_formats::effect::shot_markers`, `pd_convert shotpoints`). Corrections to the paragraph above:
- The `SHOTnn` joints are in **slot 1** models, not slot 0: the function reads the effect definition's slot-1 list (`def + 0xf4 + 0x1c` = `0x110`, models from `0x114`) whichever instance handle it is given (the running cast effect, `fighter + 0x13b20`). Measured over all 496 effects: 73 effects carry markers, 86 marker joints, every one in a slot-1 model (the projectile body) -- the cast slot 0 never has one. The test is `(name & 0xFFFFFF00) == 0xB3D8C5xx`; the index is the two digit characters `10 * tens + units`; marker `nn` fills object slot `nn - 1`, the count is the highest `nn`.
- **The marker is a fixed offset in the caster's frame, not an animated bone**: the program builds `joint translation * effect matrix` (rows 0-2 and the translation row of the effect instance's matrix = the caster's own matrix, root at the feet), reading the joint's raw translation from the model data -- no animation is applied to effect joints. So the spawn point of every marker skill is one constant per effect (right-handed, x right / y up / z forward at yaw 0): Laser `eft0042` (0, 14.38, 10); Blaster `eft0053` (0, 14.38, 10); Double Laser `eft0045` (13, 12, 0) and (-13, 12, 0); Triple `eft0211` (13, 5, 10), (0, 27, 10), (-13, 5, 10); Octo `eft0281` eight times (0, 13, 7); Ricochet `eft0050` (-5, 19, 10), (5, 19, 10), (5, 9, 10), (-5, 9, 10); `eft0096` / `eft0097` (0, 0, 0) (on the feet). `pd_convert shotpoints --list` prints all of them. The object keeps the caster's own orientation: only the **translation row** of the fire matrix is replaced by the marker's.
- **Several markers**: shot `i` of a cast takes marker `(counter + i) mod count` (`local_c8[iVar5 % count]`) where `counter` is the fighter's running shot counter (`fighter + 8`) -- the same number that picks its angle step, so a fan shot always leaves from the marker of its own angle.
- **No marker in the effect (every melee skill, Psycho Wave and the other palm / kick / punch skills, the swords, Bomb Shot, the Rain / Meteor / Spike skills): the right hand.** When the scan finds none, `FUN_14018a310` returns the owner's `RHAND` bone matrix (packed name `0xADB07630`, looked up in the per-player bone table `FUN_14018aa50` that `FUN_14018a7d0` rebuilds from the skeleton every frame), so the object is made at the hand's position *at the fire frame of the cast clip*, and melee reads that matrix **every tick of its hit window** (punch sphere centred on it; sword blade from it along matrix row 2, the bone's local +Z). A short table at `0x1402dbd58` (effects 45, 211, 281 -> 2, 3, 8 copies of the hand matrix) covers the multi-shot effects when a marker scan comes up empty.
- Exported for the sim (which must not read animation state): `cache/shotpoints.json` (`markers`: effect number -> offsets in marker order) and `cache/chars/<id>.hand.json` (per character, per `ATK_*` clip, the `RHAND` position and +Z axis at every 30 fps clip frame, root translation kept at bind like the glb). Regenerate: `pd_convert shotpoints "<Data dir>" "<cache dir>"` (about a second). The sim picks the effect through the action row (ground / air effect number) and the hand frame from the row's fire tick.
- Unconfirmed: that `fwd` (bone +Z) is the sword's blade direction in the program's own space after our z mirror (the 12 u hit radius around the target makes sword hits insensitive to it); charge skills read the hand at the row's fire tick although their clip holds a loop first; Crystal Wall and the other guards have no marker and are not made through this path (they stand on the caster).

## Effect ALR pieces

A model's draws are the pieces. Each 0x2 index buffer is preceded by a **0x13 chunk (128 bytes = 32 words)** holding its timing. A 0x13 can instead precede a **0x14 chunk** (44 bytes): a piece drawn by a game shader rather than from geometry, timed by that 0x13. 14,739 of 14,745 draws have a 0x13.

### 0x14 shader-drawn pieces

Payload: +0x08 two u32 = the kind, +0x10 u16 material (this model's 0x1 table → texture), **+0x12 u16 transform joint** (was read as a "counter"; 2026-09-27: eft0003's BLADE01 → joint 5 = RSWORD, PARTICLE01 → 2 = RHAND; see "Where pieces attach"). ✅ layout from dumps of all 3,767.

**The kind is the emitter class's packed name** ✅ (2026-09-27, knifefx lane): the two words decode with the same base-40 scheme as shader and joint names — `4ca477d9 0c350000` = **BLADE01**, `…124f8000` = **BLADE02**, `650e9921 0c350000` = **FLAIR01**, `a07ac685 8891f680` / `…fcc0` = **PARTICLE01 / 02**, `90e7fd3e 760929ea` / `…e9` = **MSPARTICLE01 / 00**, `b8de89ea 00000000` = **TALE01** (trail), `893e3f31 124f8000` = **LIGHT02**. The program has the matching strings (`BLADE01` … `ykPARTICLE01` at file offset 0x2ef280), classes (`pdEftBlade01`, `pdEftFlair1`, `MSParticleFunc`, …) and shaders (`Blade01V_vs.cso`, `Flair1P_ps.cso`, `Tale01P_ps.cso`, … in `game_files`).

- **BLADE01 / BLADE02 — the sword's swing ribbon** ✅ reading, ⚠️ look (`pdEftBlade01`, set-up `FUN_14010b140`, vtable `0x140479bf0`: init `FUN_14019e820`, draw `FUN_14019ec80`, sample `FUN_14019f450`). Used only in the swords' slot 0, windowed on the hit (Psycho Knife 17–23, Excalibur / Psycho Blade 18–32, Muramasa 18–33; 16 files). Each effect frame inside `start..end` it records the emitter's world matrix (its joint on the bone, RSWORD for every sword); it keeps `end − start + 2` samples, and draws a triangle strip between the bone point and a point **word 28** units along the bone's axis (program: −word28 × the left-handed Z row = +Z in ours; Psycho Knife 13 (= its blade reach s64 × 0.1), Psycho Blade 18, Excalibur / Muramasa 20, Mist Blade 33 — not the reach for those: Excalibur and Mist Blade reach 30), smoothed with **word 1** spline steps between samples (`FUN_14017e120`), vertex alpha ramping in / out over the first / last half-sample. u runs base → tip, v newest → oldest sample (the textures agree: eft0003 tex 4 is a magenta sweep bright along the tip edge and leading edge). After `end` the ribbon stays where it is for **word 0** frames while its colour goes word 12 → word 13 (Psycho Knife white → transparent). Words 10 / 11 pick easing curves and 24–27 a scalar range fed to the shader ❓ (ours: linear, ignored). Additive. Drawn by `effects::FxBlade` (world-space mesh rebuilt each frame).
- **FLAIR01 — a ray burst** ✅ reading, ⚠️ look (`pdEftFlair1`, spawn `FUN_14010c480`, rays `FUN_1401a1170`, geometry `FUN_1401a1620`; 102 uses, 73 in cast slots — the strike's starburst). While on (Psycho Knife frames 13–14, on RHAND) it fires **word 30** rays per frame (16), each living **word 31** frames (4), each a flat wedge from the centre out to `length` with `width` across its tip, in a random 3-D orientation: length word 4 → 5, tip width word 8 → 9 over its life when words **24 / 25** are 0; when set (all 102 emitters, Psycho Knife included) each ray draws its own random length r × (word 6 − word 4) → r′ × (word 7 − word 5) and width r × (word 10 − word 8) → r′ × (word 11 − word 9), r uniform 0–1 — see "Effect units (2026-09-28)" (corrected 2026-09-28; was read as words 22 / 23 with a fixed size), colour word 12 → 13 (mode word 29; 1 = random between words 12/14 and 13/15 — not read), word 19 = placement (1 = position only). Additive, its texture. Drawn by `effects::FxFlare`.

### Skinned/palette pieces (vertex format 0x20) ✅ 2026-09-28

Two effects — `eft0600` ("aura", the on-character glow wisp; docs/CAPSULE-VISUALS.md "Probe results 2026-09-28" lead 1) and `eft2001` — have draws whose vertex buffer format is **0x20**, not the plain textured-quad format (0x01 etc.) every other effect piece uses. `pd_convert drawinfo`/`joints` on `eft0600.alr` show it is byte-identical to the character body's skinned format (`VERTFMT_CHAR_SKIN` = 0x11, `character.rs`'s "SWBOS": pos f32×3 @0, UV i16×2 @12 (/32767), blend weight bytes @17/18, two shader-register slots @20/22) with a 7-entry bone `palette` per draw — just filed under a different format id (`VERTFMT_EFFECT_SKIN` = 0x20, `pd_formats::alr`).

Before this was recognised, `alr::vertex_layout` had no table entry for 0x20, so the generic reader fell through to the untextured default (stride 12, no UV) and the exporter's `ua.is_none() && !opts.include_untextured` check dropped the draw entirely — the geometry, indices and texture all existed (confirmed with `texprobe`/`drawinfo`) but `pd_convert effects` produced a `.glb` with **zero meshes** for it, silently.

Fix (`crates/pd_formats/src/alr.rs`, `gltf.rs`; reuses the same reading `character.rs` already did for character bodies, moved to `alr::{SkinVertex, read_skin_vertices, palette_joint}` so both call it): `gltf::export_glb` now recognises a draw whose vertex format is `VERTFMT_CHAR_SKIN` or `VERTFMT_EFFECT_SKIN` and has a palette, and computes each vertex's position as the weighted blend of its up-to-two palette joints' bind-pose transforms (the same math the game's vertex shader does), instead of reading the raw local position at face value. For `eft0600` this is a no-op in practice — its 7-joint chain's bind pose is all-identity, so the blended position equals the raw local position and the draw's own placement joint (`transform_idx`, e.g. `RHAND`) does the actual placement, as for any other piece — but the general blend is correct for a palette with real bind offsets too.

One-off audit (`pd_convert fxgap <Effect dir> [skills.json]`, 2026-09-28): of all 539 converted effects, exactly **2** had a format-0x20 draw silently dropped before this fix — `eft0600` and `eft2001`. Cross-referenced against `cache/skills.json`'s `action.ground/air.effect` (the same lookup `pd_game`'s `SkillFx::load` uses, `crates/pd_game/src/fx.rs`): **no skill uses either number** as its cast effect, so this had no visible effect on versus-mode skill playback — `eft0600` is the character-glow effect (not yet confirmed wired to anything at runtime; see CAPSULE-VISUALS.md) and `eft2001` is outside the 0–999 skill-effect range (a story/system effect, out of this rebuild's scope per AGENTS.md).

Verified in `pd_viewer --fx` (`chars/pc00a`, stage `st01` to avoid st06's water fog at ground level, since the viewer plays a test effect "root only" — at the effect's own spawn point, not reparented to a character bone, unlike in `pd_game`): `eft0600` now shows a bright white/grey streaky wisp burst (`shots/fxgap/eft0600_st01.png`; before, nothing: `shots/orb/eft0600_f20.png`); `eft2001` shows a large green/magenta/white ray burst (`shots/fxgap/eft2001_st01.png`). Regression-checked three ordinary (already-working, non-skinned) skill effects through the same exporter path: Psycho Wave (`eft0001`), Laser (`eft0042`), Crystal Wall (`eft0115`) — all still render (`shots/fxgap/regress_*.png`).

### Shaders (material entry words 0–1) ✅ 2026-09-27

The first two u32 of every 0x1 material entry (0x4C bytes) are the draw's **shader name**, packed 6 characters per word in base 40 (0 = end, 1–10 digits, 11–36 letters, 37 `_`; most significant first — the game's packed-name scheme, see Esper-RE `ssb.c` notes). They name the game's own shader files (`game_files/<NAME>_ps.cso`): over all 14,739 effect draws — `PDEFTBB01` 11,595, `PDEFTBB02` 1,154, **`PDEFTOPT05` 1,120**, `PDEFTBB01R` 215, `PDMTEX01` 196, `MSICE11` 86, `PDEFTBB04` 83, `PDEFTBB01C` 74, `YKREFRECT00` 65, `PDEFTBB03`, `PDEFTAURA01`, `PDMTEX02`, `PDEFTFILLET0`, `PDEFTOPT05N/05C/06/03`, `YKEDGESLUR00`. Exported per piece as `shader` in the `.fx.json`.

Disassembly (`tools/disasm`): `PDEFTBB01/01R/01C` = texture × vertex colour, alpha = tex.a × colour.a, alpha-kill. **`PDEFTOPT05` reads texture 0 as signed offsets (G/B − 0.5, through a `bumpenv` matrix) and samples a second texture at the offset UV** — a bump-offset **screen distortion** (heat haze), not a colour; its vertex shader builds that second UV from the projected position plus `cSCREENOFFSET`, i.e. the second texture is the screen. (`MSICE11` instead reflects: its vertex shader uses the normal and `cEYEVEC`; drawn additively its pieces show as white chunks, e.g. Bomb Shot's landing ❓.) Its textures agree: R is flat in 162 of 268 of them (2-channel offset maps, e.g. Psycho Wave's cyan sine stripes) against 49 of 1,670 for `PDEFTBB01`. Drawn additively they were the big cyan striped swirls over Psycho Wave and other casts. **Playback now hides `PDEFTOPT03` / `05*` pieces** (`PD_FX_DISTORT=0.2` shows them faintly, `1` as before); proof `shots/fxlane_pw_ab.png`.

### ✅ The `01`/`01R`/`01C` suffixes are render state, not different shaders — the `.cso` files are byte-identical (2026-09-28)

The long-standing ❓ on these suffixes is settled. **`PDEFTBB01`, `PDEFTBB01R`, `PDEFTBB01C` and `PDEFTBB01P` are the *same file* — all four `_ps.cso` are 1,336 bytes with md5 `e4333ef11490…`, and all four `_vs.cso` are 1,560 bytes with md5 `59e452bebc15…`.** The disassembly is identical instruction for instruction. So:

- **The shader cannot tell them apart**, which means the difference the suffix names is **entirely in the fixed-function render state** (blend op, blend factor, alpha-test, depth write, cull) set by the material's `+0x14` u16 — the field FORMATS-EFFECTS already flags as "blend from material u16 +0x14 via `FUN_1402a6010` → `FUN_14028e4e0`, tables `0x1402f77c0` / `0x1402f7798`, GL enums".
- ❓ **Which state each suffix means is still unread.** The name→state mapping is not in the `.cso`. The leads I chased, and where each ended (2026-09-28):
  1. The tables at `0x1402f77c0` / `0x1402f7798` are a **false trail** — they hold **GL-era enums** (`0x8001` GL_ONE, `0x300` GL_SRC_ALPHA, `0x8006` GL_ONE_MINUS_SRC_ALPHA, `0x800A` GL_ONE_MINUS_DST_ALPHA), leftovers from the Xbox 1 build and dead on PC.
  2. `FUN_1402a6010` reads the material's `+0x14` u16 and then `FUN_1402a5f60` — but `FUN_1402a5f60` turns out to be the **near-camera 32-level stipple fade** (it selects a stipple pattern from bits of the draw-state word at `param_2 + 0x30` and calls the D3D stipple-pattern setter), **not** the blend path.
  3. The blend *is* set in `FUN_1402a6010` via `FUN_140020c40(stage, cap, op)` / `FUN_140020660(0x4b…)`, driven by the draw-state word at `param_2 + 0x30` — so **the material, not the shader name, selects it** ✅.
- **So the suffix is not the selector at all** — that part of the old guess is now wrong, not merely unproven. What survives: all of `PDEFTBB01*` run one identical program, so every visual difference between them is fixed-function state coming from the material, **which our converter already reads**. ⚠️ Mapping the draw-state word's bits to specific D3D blend ops, and correlating that with the `R`/`C`/`P` naming, is still open — the constant-cache writer `FUN_14001e540` has **171 call sites**, so it needs the specific per-draw path, not a text search. Not worth more time now: the visual outcome is already close (the "dark blob" fix), and this would only refine dark-skill blending.

### Wider: the `.cso` set is a **name registry**, heavily aliased (2026-09-28)

Hashing all **437 `.cso` files** gives **318 unique contents in 69 duplicate groups** — so ~27 % of the shipped shader files are byte-copies of another file under a different name. The groups are real shaders, not stubs (median file 1,916 bytes; the largest group is eleven 1,308-byte pixel shaders: `Filter1P`, `Flair1P`, `PDEFTBB04`, `PDEFTOPT01`, `Part2P`, `SCA2`, `Tale01P`, `Thunder2P`, `pdevdefault3D_p`, `pdevdefault_p`, `qdraw`). Other groups: `SSHADOW`/`SSHADOWC`/`SSHADOWCHP`/`SSHADOWP` (5), `PDEFTOPT03`/`05`/`05C`/`05N` (4), `PDMTEX01`/`01N`/`02` (3), `vkCAP01`/`vkCAP04M4`/`vkSTNCL00`/`vkSTRANGE02` (4).

**What this means:** the game ships a *named* shader registry where a name identifies a **(program, render-state) pair**, and the program half is frequently shared. **The suffix is doing the work the program doesn't.** That reframes the whole "blend state per draw ❓" question: it is not missing data in our converter, it is a second axis (fixed-function state) that the `.cso` cannot express and which we have not decoded. It also means "PDEFTOPT03 is the same program as 05" (noted above) is not a coincidence but the norm.

**Two families in that alias set are UI/debug, not effects** ⚠️ (found 2026-09-28). The 11-member group's disassembly is `texture × vertex colour` with a UV input — i.e. a plain **textured 2D/UI** shader, not a 3D effect one. The names give it away: **`qdraw`, `pdevdefault_p`, `pdevdefault3D_p`, `pdevrect_p`, `pdstline_p`, `FrameP`, `Line1P`, `Bone1P`** — "qdraw" (quad draw), "pdevrect" (dev rectangle), "pdstline" (dev status line), and the `Frame`/`Line`/`Bone` trio. **None of them appears in the decompiled program** (0 references in `decomp_all.c`; they exist only as file names in the binary's string table), so the PC build ships them but the code we can see doesn't reach them ❓ — consistent with a retained debug/UI path. **We have never looked at these in any doc**, and they are the reason the "11 identical shaders" number looked so odd: it is mostly UI, not eleven game systems sharing a program. Worth knowing before anyone reads that group as a finding about effects.

✅ 2026-09-27: **`PDEFTOPT06` and `YKREFRECT00` are not distortion** and are drawn again. `PDEFTOPT03` is the same program as `05` (distortion). `PDEFTOPT06` outputs texture 0 mixed with two reflection lookups, alpha 1 — a solid shiny surface: it is the mines' shells (Timer / Sensor / Remote Mine flight slot) and parts of Antigravity Trap and others. `YKREFRECT00` outputs texture 0 × colour + a reflection map × texture 2, alpha = the colour's — a reflective solid: **Muramasa Blade's and Rail Gun's blades** (eft0030, 0039, 0132, 0512). ### Camera-dependent "dark blob" / milky orb: a rendering bug, not a data gap ✅ 2026-09-28

Confirmed against the disassembly quoted above (`PDEFTBB01/01R/01C` = "alpha-kill", i.e. an opaque alpha-**test** cutout, not a smooth alpha **blend**) and against Bevy's own pipeline (`bevy_pbr-0.19.1/src/render/mesh.rs::specialize`): `AlphaMode::Blend`/`Add` both draw in the sorted transparent pass with `depth_write_enabled = false`, so a **double-sided mesh drawn with `AlphaMode::Blend` and `cull_mode: None` has no fixed order between its own front and back faces** — Bevy doesn't sort a single mesh's triangles, only entities against each other. Three render paths in `pd_game` did exactly this:

1. **Idle capsule/Aura Particle orb core** (`fx.rs::style_orb_materials`, draw `_d0`, the sphere): kept `AlphaMode::Blend` + `double_sided: true` + `cull_mode: None` "so its own swirl texture read clearly" (CAPSULE-VISUALS.md "Built 2026-09-28"). On a convex sphere this reads as a milky, opaque-ish translucent disc — self-overlapping front/back faces blended in an arbitrary order — and the *exact same instant* looks different from each split-screen camera, since each camera's view direction changes which faces draw first.
2. **Translucent puff/sprite emitters** (`effects.rs::tick_sprites`, the `s.blend && em.alpha == Some(true)` branch — the `90e7fd3e` "puff" emitter used on Laser/Slide Laser's charge per the emitter table above): drawn on a 3-crossed-plane "volumetric sprite" mesh (`[XY, ZY, XZ]`, 6 faces once double-sided) with the same `Blend` + `cull_mode: None`. Six overlapping faces with no fixed order is worse than the sphere case, and matches VFX-AUDIT.md #1 exactly: "the same effect, same tick, two different and clearly-wrong-in-one-case results depending only on which camera is looking at it."
3. **`PDEFTOPT06`/`YKREFRECT00` "solid" pieces** (mine shells, Muramasa/Rail Gun blades, `Piece.solid`): drawn `Blend` + `cull_mode: None` even though the disassembly above already says they output **alpha 1** (opaque) in the program.

**Fix** (render-only, `fx.rs`/`effects.rs`; `sim.rs`/`combat.rs` untouched): all three now draw single-sided with normal back-face culling, and use a mode that doesn't need a sort:
- `solid` pieces → `AlphaMode::Opaque` (matches the program's own alpha-1 output) + `cull_mode: Some(Face::Back)`.
- Translucent puffs → `AlphaMode::Mask(0.5)` (matches the disassembly's "alpha-kill") + `cull_mode: Some(Face::Back)`. `Mask` draws in the opaque pass (depth-tested and depth-written like any solid geometry), so overlapping faces resolve per-pixel by depth, the same way from every camera.
- Orb core → single-sided `Opaque` (see "Idle orb: dark core + fresnel rim" in CAPSULE-VISUALS.md).
- **Bomb / Timer Mine opaque slab, fixed 2026-10-01 (fixbomb lane)**: the translucent-puff cut-out is only for puffs whose own material alpha-blends (dest factor not ONE, e.g. `0x5400`). Bomb's (`eft0031`) and Timer Mine's slot-2 puffs (MSPARTICLE01, state `0x1400` = SRC_ALPHA, ONE, texture a dark red disc with alpha) are *additive*; the `em.alpha` heuristic alone had them alpha-cut at 0.5 and depth-written, which at the slot-2 impact scale (blast radius x 0.2: Bomb x6, Timer Mine x10 -- applied to the effect root, so puff sizes ride it like the program's `FUN_14010f710`, which copies the instance matrix into each particle) became an opaque dark-red stepped slab hiding the opponent. `Sprite.additive` (dest factor ONE) now routes them to `AlphaMode::Add`; test `an_additive_puff_is_never_the_opaque_cutout`. Bisect: `PD_FX_BLEND` / `BILLBOARD` / `CULL` / `LATCH` all left the slab; hiding the slot's pieces left it; hiding the puff emitters removed it. The x6 scale itself is right (root matrix); the puff size scaling with it is the program's reading but not separately confirmed. Big Bomb, Photon Wave and an ordinary hit (Throwing Stone) are unchanged by the fix (no additive alpha puffs). Sheets `engine/shots/fixbomb_sheet_*.png` (local).

Additive pieces (`AlphaMode::Add`, the overwhelming majority of effect draws) were not changed: Bevy's `Add`/`Premultiplied` blend state is a pure sum, which is commutative — draw order never matters for it, so it was never the source of this bug and needs no sort.

**Proof**: `PD_TEST_PRESS=240,0,225 PD_SHOT_TICKS=p0,p57 PD_TEST_SPLIT=tb --stage st04 --near --loadout 65,65,65,65` (Laser) and the same with `p0,p29,p50 --loadout 66,66,66,66` (Slide Laser) — before: `shots/vfxaudit/laser_tp057.png` / `slidelaser_tp050.png` (bottom split view: opaque dark-navy blob swallowing the caster); after: `shots/vfxaudit/after/laser_tp057.png` / `slidelaser_tp050.png` (both split views now show the same clean glow) and `shots/vfxaudit/after/sheet_*_before_after.png` (montaged side by side). Not committed (game-derived screenshots).

### Blending: the game adds in gamma space ✅ (2026-09-27, knifefx2 lane)

None of the game's pixel shaders converts to or from linear light (effect shaders `PDEFTBB01`, `Flair1P`, `Part1P`, `Blade01P`, stage `SD`, character `SWBOS`: texture × vertex colour, clamped, straight out), so its additive effects add the stored 0–1 values onto the screen's. Bevy decodes them to linear light, adds there and tone-maps every fragment (TonyMcMapface, the Camera3d default), so the same piece adds a fraction: a 0.5 glow over a 0.35 floor gives 0.62 on screen instead of 0.85, and ten overlapping dim sparks never reach white. That was most of "lacking the brighter FX". `effects::FxMaterial` (= StandardMaterial + `fx_gamma.wgsl`) re-encodes an additive fragment's colour (x^(1/2.2), exact for a product of decoded values) and skips the tone mapping, so it adds what the game adds; blended draws are unchanged (over a dark background a faint glow now reads brighter than the game's, over the scene much closer ⚠️). `PD_FX_GAMMA=1` gives the old blending for A/B. The MSPARTICLE puffs keep the old blending (their reading is still unconfirmed and at full strength Psycho Knife's hit puffs read as a big white cloud). Every shader also writes a constant `blend_colour` to a second render target (a glow / mask buffer ❓; `GFilter` / `glow` filter shaders exist) — not reproduced. Proof: `shots/kfx2_pk_burst_zoom.png`, `kfx2_laser_blaster_footage.png`.

### A rendering regression was caught and reverted before merge: an alpha-kill guess reproduced the "dark blob" bug ✅ 2026-09-28 (lane-charge)

An earlier iteration this same session tried to also fix Slide Laser's missing "huge green crescent sweep at cast onset" (`FOOTAGE.md`; `ft_slide_laser_cast_and_fire.png` f0018-f0029, T+0 to T+367ms), on this reasoning: `eft0043`'s cast model has a 5-piece family (`m0_d4`..`m0_d8`, frames 8-40, `grow` +220% to +360%) whose colour (words 12/13) fades **white/transparent → black/opaque** — the opposite direction from the majority "white opaque → transparent" fade-out family (see "0x13 words" above) — which looks like the natural end-state of an **alpha-kill cutout** draw (`PDEFTBB01`'s disassembled behaviour: alpha-test, not a blend — "Camera-dependent 'dark blob'" above already established this reading for the puffs and `solid` pieces), not of an additive glow. Drawn as `AlphaMode::Add` (every plain quad piece's default), the reasoning went, this family was rendering as close to nothing (`Add`'s output is `colour.rgb x colour.a`, and this family's rgb heads to `(0,0,0)` exactly as its alpha rises) — so it was switched to `AlphaMode::Mask(0.5)`, matching the puff/solid treatment.

**This was wrong, caught by screenshot review, not further analysis**: switching to `Mask` makes the piece's *actual displayed colour* (texture × vertex colour) the thing shown once past the alpha threshold — and that colour is the same one heading toward black. The result was a real, solid, dark quad drawn over the caster: exactly VFX-AUDIT.md #1's "dark blob" bug, reintroduced by this change, on Slide Laser's own charge. **Reverted**: this family is plain `Add` again, like every other quad piece (`effects::attach_pieces`, the `solid`/`Opaque` branch is the only exception left). Re-checked against the raw words while reverting: word 9 (scale easing) **and** word 10 (colour easing) on this family are both `2` ("fast start") — an earlier pass mis-read word 10 as `0`/linear; corrected here. Under `Add`, fast-start colour easing means this family still rises and falls within its own window (its rgb and alpha both ramp up quickly then hold), so it isn't literally invisible, but it doesn't reproduce the footage's fast, blown-out flash either — see "Still open" below. Laser (`eft0042`) has no piece family with this colour direction at all, which is at least consistent with the footage only calling out a Slide-Laser-specific element.

**Still open / unconfirmed**: which piece(s) actually draw the footage's green crescent hasn't been pinned down with confidence. The `m0_d4`..`m0_d8` family remains the leading candidate by position (root-anchored, in front of the chest) and rough timing (windowed frames 8-40, i.e. 267-1333ms, overlapping the footage's ~150-800ms), but its colour fading toward black argues against a simple "just make it brighter" fix, and reinterpreting that colour data (e.g. as an alpha-only envelope over the texture's own colour, ignoring the RGB tint) is a real hypothesis but unverified against the disassembly or the program — flagged for a follow-up with dedicated reverse-engineering budget, not guessed at again this session. Direct footage-vs-render comparison sheets (`shots/vfxaudit/charge/sheet_slidelaser_vs_footage.png`, `sheet_laser_vs_footage.png`) show the general oversizing fix (above) does make both moves noticeably closer to the footage's compact swirl even without this crescent.

## Render semantics (2026-09-30, lane fxrender) ✅ reads, ⚠️ looks

Built from `audits/P0-EFFECTS.md` Lane A after re-reading each claim in `decomp_all.c`, the PE and the shaders (`tools/disasm`). Code: `pd_formats::effect::BlendState` (decode + tests), `pd_convert effects` (writes `mat_flags` / `mat_state` per piece and emitter; **re-export needed**: `pd_convert effects <Data/Effect> <cache/fx>`), `effects.rs` (`Piece`, `FxGamma` specialisation, `animate_pieces`), `fx_gamma.wgsl`. Old caches without the two fields keep the old additive draw.

**Blend state** ✅ (`FUN_1402a6010` -> `FUN_14028e4e0`, tables `0x1402f77c0` / `0x1402f7798`, D3D mapping `FUN_140020420` / `FUN_1400204f0`). Material entry `+0x0C` bit `0x10` = blending on, else opaque with an alpha test; `+0x14` u16 state: source factor = bits 8-11, destination = bits 12-15, operation = bits 5-7. Factors 0..10 = ZERO, ONE, SRC_COLOR, 1-SRC_COLOR, SRC_ALPHA, 1-SRC_ALPHA, DST_ALPHA, 1-DST_ALPHA, DST_COLOR, 1-DST_COLOR, SRC_ALPHA_SAT; 11-14 map to D3D11 dual-source factors (fed by the pixel shader's `o1 = blend_colour`; unseen in skill effects, drawn as ONE); operations ADD, SUBTRACT, REVERSE_SUBTRACT, MIN, MAX. Measured over every piece in the 539 exported effects: `0x1100` ONE,ONE 8,244 · `0x5400` alpha 1,838 · `0x1400` SRC_ALPHA,ONE 1,541 · `0x1800` DST_COLOR,ONE 1,230 · `0x1200` SRC_COLOR,ONE 803 · `0x3000` ZERO,1-SRC_COLOR 725 · blending off 289 · a few reverse-subtract / min-max states. Ours: the state goes on the wgpu pipeline (`FxGamma::specialize`); `fx_gamma.wgsl` encodes the colour for the factor it meets (gamma-exact for the multiply family).

**Alpha rule** ✅ (corrects the audit's D8). `PDEFTBB*_vs` computes `o1.xyz = v1.w * (v1 * c35).xyz`: the colour is **premultiplied by its own alpha in the vertex shader**, so with ONE,ONE a fading colour alpha *does* dim the piece (the audit said it never attenuates — that is wrong). What ONE,ONE does not use is the **texture's** alpha (`PDEFTBB01_ps`: `o.rgb = tex.rgb * colour.rgb`, `o.a = tex.a * colour.a`, alpha only kills/feeds SRC_ALPHA factors); ours used to multiply by it. `PDMTEX01/02` and `msEFTBB01S` pass the colour straight. A piece at colour 0x00FFFFFF -> 0xFF000000 (Slide Laser `m0_d4..d8`, ONE,ONE) is therefore a brief glow peaking at 25%, not a white flash.

**Word 19** ✅ (corrects the audit's D2 / D9). It is a three-valued float: `0` = billboard (`FUN_1401a5ff0` compares with 0.0), `1` = mesh in its own orientation, `2` = mesh **without culling** (`FUN_14011bc30` / `FUN_140116ae0` compare with the constant at `0x1402f2a10` = **2.0** and set cull none, else `0x901` = cull back). So culling is on for modes 0 and 1 and off only for 2 (the audit had it reversed). Over the exported pieces: BB01 2.0 x5,291 / 0 x4,223 / 1 x558, all 1,398 `MSEFTBB01S` are 0.
**Billboard** ✅: the piece's matrix becomes `view x M`, the rotation rows are replaced by the axis lengths (scale only), rolled in the view plane by word 7 x move curve, then projected: the quad (and any mesh with word 19 = 0) keeps its position but its local x / y / z follow the camera's right / up / depth, rotating the quad's coordinates first, then scaling. `fx_gamma.wgsl` does this in the vertex stage from `view.view_from_world`, so each split-screen camera gets its own facing (a CPU transform could serve only one). **Roll** ✅ (`FUN_140290800`): degrees x curve truncated to an integer, `deg * 0x8000 / 0x168`, modulo 0x8000, X axis turns towards Y (counter-clockwise on screen); applied to meshes too (about the piece's Z). `roll_radians` and the billboard basis are unit-tested.

**MSEFTBB01S** ✅ read, ⚠️ size: the class's draw (`FUN_140115ca0`, vtable `0x14047a4c0`) does **not** draw the exported quad; it appends one point per piece (position = the piece origin, size `min(|axis x|^2 * 65534, 32767)`, colour = the lerped ARGB) to a point ring that `FUN_14001dbe0(1, ...)` draws as D3D points, which the port expands with `msEFTBB01S_vs` (`vertex_id` picks the corner from `quad_pos[6]`). The vertex shader sizes the point by `size * cb0[32].x * (0.001172, 0.002083) / (2w)` in clip space, i.e. about 1/w^2 on screen; `cb0[32].x` is written elsewhere and **unread**, so the point's real size is unknown. We draw a camera-facing billboard of the exported quad's own size (the same world size as before, but facing the camera), no culling, colour straight. The audit's "constant on-screen size" wording was self-contradictory (size ~ 1/w is the ordinary perspective shrink); no constant-size claim is made.

**Easing curve 2** ✅ (audit D13): the pieces' helper `FUN_1401a5ff0` *and* the blade's `FUN_14019ec80` use `e (2d - e + 1) / (d (d + 1))` (reaches 1 at e = d); the old `e (2d - e - 1)` belongs to `ykEDGESLUR00` (`FUN_140122ac0`). Fixed for pieces, blades and lights (one `curve`); the test pinned the wrong numbers.

A/B switches (for sheets): `PD_FX_BLEND=0` (all pieces additive as before), `=2` (the program's blends except the multiply-darken ones, which stay additive), `PD_FX_BILLBOARD=0`, `PD_FX_CULL=0`; `PD_FX_FRAMELOG=1` prints frame-to-frame wall time.

## Piece timeline and pixel stage (2026-10-01, lane fxtime) ✅ reads, ⚠️ looks

Built from `audits/P0-EFFECTS.md` Lane B plus the per-shader pixel stage, after re-reading each claim in `decomp_all.c` and the shaders (`tools/disasm`). Code: `effects.rs` (`animate_pieces`, `latch_pieces`, `piece_colour`, `flipbook_cell`, `cell_uv`, `shader_family`), `fx_gamma.wgsl` (families), `pd_formats::effect` (`mat_tex` / `mat_addr` / `vertex_format` / `vertex_colour` per piece), `pd_convert effects` (second textures as `eftNNNN_t<index>.png`, vertex colours as `COLOR_0` in the glb). **Re-export needed**: `pd_convert effects <Data/Effect> <cache/fx>` (old caches keep working: no vertex colours, family pieces fall back to the plain path).

**Clock and window** ✅. `FUN_1401899b0` adds the step at `+0xf068` to each live instance's frame once per update; the only writer of that step (`FUN_140189830`, manager init) sets `1.0`, so the program's frame is a whole number and every "fraction" below is 0 unless a mode builds one. The piece is drawn while `start <= frame <= end` (`FUN_140188fd0`, the end included); the instance is dropped only when `duration < frame` (strictly), i.e. its last frame is drawn too (the audit said "removed when t >= duration": off by one frame). Ours: smooth clock, window `floor(frame)` in `start..=end`, despawn at `age >= len + 1`; `PD_FX_STEP=1` runs whole ticks (audits question 3 is still Laurence's).

**Flipbook** ✅ (`FUN_1401a5f20`; the two-texture classes' `FUN_1401a8510`). Word 21 is tested as an integer: 0.5 / 0.3 / 0.2 (37 pieces) count as 0. 0 = one cell per tick, `(floor(frame) - start) mod cells` (the program also adds `(float)u16` at the draw record `+0x3e`, never seen non-zero, taken as 0); non-zero = stretched, `cell = trunc((frame - start) / d * cells)`, `d = end - start + 1` (ours used `/ (end - start)`). Words 24-27 are **not** read by this class (the old "frame range" was a no-op on every real piece; removed). The cell goes to the vertex shader as `(1/cols, 1/rows, col, row)` and the shader computes `scale * (uv + cell) + scroll`.

**UV scroll** ✅ (`FUN_1401a5ff0`, constant `0x22`): `(w22, w23) x move curve`, a translation in **texture units added after the flipbook scale** (not in cells). Applies to texture 0 only (`PDMTEX01_vs`: `o2.xy = uv`, `o2.zw` = flipbook + `cb0[34]`).

**Colour** ✅ (`FUN_1401a9ae0`): `lerp(start, end, k)`; word 30 non-zero and an **odd whole frame** -> the pair (14, 15) instead of (12, 13); word 31 `w` > 0: `k` runs the colour curve over the first `w` frames (`e < w`, taking priority), holds 1, and over the last `w` frames (`end - frame < w`) runs the curve with ease-in/ease-out **swapped** (1 <-> 2, 0 stays) from 1 down to 0, so the colour returns to its start value on the last frame. Word 29 (clamp to start / end) only touches frames outside the window, which are never drawn: a no-op (audit: "16 pieces" -- they are unaffected).

**Word 28, root-matrix modes** ✅ (`FUN_1401a5940`). 1 and 2 look the piece up by (instance id, draw record) in a table of 256 matrices (`FUN_14018e880`; store `FUN_14018a9b0`): a miss stores the joint's matrix as it is **at the first frame the piece is drawn**, a hit draws from the stored copy. Mode 1 = the stored matrix; mode 2 = the stored **position**, the **live** axis lengths of the joint matrix, world-aligned axes. The piece's own move / grow / roll run on top in that matrix's axes. Ours: `FxLatch` keeps the world matrix of the piece's parent (bone or effect root) at its first visible frame and `latch_pieces` (PostUpdate, after transform propagation, before visibility checks) sets `latched parent x local` as its and its mesh's GlobalTransform (mode 2: `T(latched position) x S(live scale) x rel`). Counts over skill effects: mode 0 9,768, 1 4,354, 2 585, 3 4, 5 30, 6 22 (the school aura's `eft0600`), 8 12. **Not built**: 3 / 7 (the instance's live root matrix, `+0xa0` / `FUN_14018a8b0`), 5, 6, 8 -- they play as 0. Corrections to the audit's D3: modes 4 and 8 **write into the instance root matrix in place** (4 stores the joint's scale on its diagonal, 8 stores the joint's position), 8 keeps the root's orientation, 6 is the joint's own position and scale with world axes (used by the aura wisps); and the "slot 3 / slots 1-5 keep the spawn matrix" half of D3 is **not** done (it needs `fx.rs`: lane FX-C).

**Vertex colours** ✅ new. `PDEFTBB*_vs` / `PDMTEX*_vs` multiply the piece colour by the vertex colour (`mul r0, v1, cb0[35]`), and 7,934 of 10,073 plain `PDEFTBB01` pieces (and 640 of 1,398 `msEFTBB01S` draws) have **non-white vertex colours** (soft edges, gradients) that the exporter dropped. Now `COLOR_0` (linear from the gamma-space BGRA bytes); the shader's premultiply weight includes the vertex alpha (`o1.xyz = v1.w * (v1 * c35).xyz`).

## MSPARTICLE blend 1 is an alpha blend, not an opaque cut-out (lane fxfix, 2026-10-03) ✅ read, ⚠️ looks

**Symptom (Laurence): Rapid Cannon "produces a thick black smoke that obscures the user's view".** Cause, from the data and the program:
- `eft0048` (Rapid Cannon) emitter 0 (MSPARTICLE `...e9`, on RADDHA, cast frames 14-15, count 5, life 30, size 5 growing +0.5 a frame = 5 -> 20 u) and emitter 9 (slot 2, the muzzle blast) author **word 26 = 1** with colours `0x337f7f7f -> 0` / `0xffffe5b2 -> 0`: a puff whose **colour alpha** goes 20 % -> 0 (and 100 % -> 0). 85 effects (315 emitters, 91 skills, 49 of them attacks: Rapid Cannon / Trench Mortar / Fire of Gehenna / Jack Pot / Meteor / Rain of Stones / Root of Tree ...) use word 26 = 1.
- READ `FUN_14010e260` (the MSPARTICLE draw): word 26 = 1 sets the blend `FUN_14028e4e0(0x5401)` = source SRC_ALPHA, destination 1 - SRC_ALPHA (factor tables `0x1402f77c0`, bits 8-11 = 4, 12-15 = 5; the same decode as every other draw, "Render semantics"). It is an ordinary alpha blend.
- The pixel stage (`vk_billbord2_ps`, disassembled with `tools/disasm`) outputs `o0.xyz = sat(texture x clamp(colour))`, `o0.w = 1.0` (a constant) and kills only texture alpha 0. **The colour's alpha is not in o0.w**, so on its own the blend would be opaque (alpha 1) with the colour fading to black: the literal reading, and what we built on 2026-10-01 (`ms_particle.rs`: "blend 1 draws opaque"). Result: Rapid Cannon's puffs became opaque dark-grey (0x7f = 50 % grey fading to black) 5 -> 20 u discs, i.e. a black cloud over the caster (`engine/shots/fxfix/before_rc/`, `final/rapid_cannon_before_after.png`). The same opaque rule gave Fire of Gehenna its full-screen orange fill and Jack Pot its black soot.
- Why the literal reading is wrong: the alpha byte of these colours is authored as a fade (0x33 -> 0, 0xff -> 0, `0x99 -> 0`) on emitters whose other words are the usual smoke settings; an opaque draw makes the alpha byte meaningless and makes "colour -> 0x00000000" a black end state, while a fade to transparent is what those bytes say. The vertex stage (`vk_billbord2V_vs`: `mov o2.xyzw, v1.xyzw`) passes the vertex colour's alpha through to the pixel stage, but the pixel stage only reads `.xyz`, so how the original turns the alpha byte into transparency is **UNCONFIRMED** (the blend/alpha-to-coverage path was not found; `FUN_1402a6010` sets alpha-test 0 only). The rule built is the interpretation consistent with the authored data: **a blend-1 puff takes its opacity from the colour's alpha byte, the same curve as the colour (`ramp_alpha`), blended SRC_ALPHA / 1 - SRC_ALPHA.** `PD_MSP_OPAQUE=1` gives the literal opaque draw for A/B.
- Test: `ms_particle::tests::blend_one_puffs_fade_by_the_colours_alpha`, `blend_words` (blend 1 = SrcAlpha / OneMinusSrcAlpha).
- Proof (tick-exact, `PD_TEST_PRESS=240,0,225 PD_TEST_SPLIT=tb --stage st04 --near --loadout 75,75,75,75`, before = exe built from main `1d1d935`, after = this lane): `engine/shots/fxfix/final/rapid_cannon_before_after.png` -- at +0.4 s to +0.6 s (p46 / p50) the caster is hidden behind a black cloud before, and a clean fireball with sparks after.

**Psycho Knife's ribbon is not a blend bug (READ, so a wrong fix was dropped).** `FUN_14019ec80` (BLADE01's draw) sets 0x5401 as well and `Blade01P_ps` outputs `(colour texture t2 + scene copy t1 sampled at an offset taken from the bump texture t0) x vertex colour`, alpha = the vertex colour's alpha. With the authored white colour `0xFFFFFFFF -> 0x00FFFFFF` that is `scene + alpha x texture`, i.e. exactly the additive draw we already use (the scene refraction is not reproduced). Slot assignment (UNCONFIRMED but consistent): `mat_tex[0]` = colour, `mat_tex[1]` = bump (eft0005's second texture is a pixel-format-8 bump map, not exportable). I tried drawing it as a plain alpha blend first; that reads as a dark purple paddle and is wrong, so it was reverted before commit.

**PARTICLE01 / 02 are point sprites (READ), drawn as one screen-facing quad** (lane fxfix). `Part1V_vs` expands each point with `quad_pos[SV_VERTEXID]` added in clip space, so a particle is a single quad that always faces the camera; ours were three crossed planes (`[XY, ZY, XZ]`), which from the side show as squares and plus-shapes. Now one `XY` quad billboarded per camera in `fx_gamma.wgsl` (`piece.x = 1`, the MSPARTICLE route); `PD_POINT_BILLBOARD=0` restores the crossed planes. The size (`POINT_SIZE` 0.0024 u per psize) stays UNCONFIRMED: `Part1V_vs` scales by `psize x (0.001172, 0.002083)` in clip space with `quad_pos` values (cbuffer `QuadMap`) that were not found in the PE.
